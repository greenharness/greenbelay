## Picture
```
plan mode file ~/.claude/plans/x.md
  front matter  plan-id: p-<26-char id>   (outside body_sha)
      │  plan-panel assigns it when absent,
      │  and a new one once the person approved that id (PostToolUse)
      ▼
  plan-review record ──► outcomes.jsonl { plan_id, round, first_round_sha }
  baseline()/save()  ──► full or delta by plan_id (panel + hook agree)
      │  worktree-task lands the file with its front matter
      ▼
  <repo>/docs/plans/<date>-<slug>.md  plan-id: p-…
      │
      ▼
  stats --time: landed plan-id ─► its rows ─► start, round-1 body, words
  relais review_outcome: reads plan_id (optional), never rejects the row
```
One id per plan, carried from the plan-mode file to the landed plan. Every consumer keys on it instead of the file path.

## Goal
The plan-review ledger has no plan identity. Rows are keyed by the plan file, and plan mode reuses `~/.claude/plans/<name>.md` for the next plan. So a later plan inherits the first plan's round 1, rounds are numbered within a transcript, `plan-panel` treats a new plan as a delta, and `stats --time` guesses which reviews a landed plan had. Measured on 2026-11-15:
- 61 plans in the first 30-day window lost their round-1 body;
- B1's own reviews were recorded as rounds 3–5;
- this plan's own panel was seated as a delta of B1's.

Each plan now gets an id the first time it goes to the panel. The id rides in the front matter to the landed plan, and the ledger, the panel/hook baseline and `--time` all key on it. The 2026-12-19 done check (t10) then reads exact rows.

The same release carries:
- B5, the panel counts (t03);
- the `--time` follow-ups left deliberate in B1's review.

## Non-goals
- Rewriting old ledger rows. Rows without `plan_id` keep the reader's landing-order split (`split_shared_starts`).
- A time estimate on the panel line: that needs four weeks of data.
- The data-names rename (`feat/greenpiste-data-names`, another session). `plan_id` is an additive field, so nothing waits for the 5.0.0 schema rename. This branch rebases on the rename if it lands first.

## Behaviour

### The plan id
- **Form:** `plan-id: p-<26-char ULID>`, a time-ordered random id, generated by greenpiste with no new crate, from `SystemTime` and `/dev/urandom` (as shadow.rs:137); off unix, or if the read fails, sha256 of time, pid and path.
- **Assigned by `greenpiste plan-panel <plan.md>`** when the front matter has no `plan-id:`.
  - It writes the line into the front matter, and creates a front matter block when there is none. It prints `assigned plan-id p-…` on stderr. It writes through `write_atomic` and only when the id is absent or retired, so a second run leaves the file byte-identical; §0 of the skill re-reads the file before the next Edit. The write happens before line 1 is printed. A failed write (a changed file, or a read-only one) prints `plan-panel: cannot write plan-id: <path>: <error>` on stderr, nothing on stdout, and exits 1.
  - `body_sha` excludes the front matter (`plan_text::canonical`), so a review is never made stale by it.
  - `plan-apply` already writes plan files, so a greenpiste command editing the plan is not new. The write uses plan-apply's protocol: hold `outcomes.jsonl.lock`, re-read the file and refuse with `plan changed under plan-panel; nothing written` when it differs from what was read, then `greenpiste_guard::atomic::write_atomic` (temp file, mode carried, rename). A test covers the refusal. The hook's `approved/` record takes no lock (see Retired at approval).
- **Retired at approval.** When the person approves ExitPlanMode (PostToolUse `on_plan_answered` with `approved: true`; the PreToolUse allow is not approval), it records `(plan_id, body_sha)` as approved under `plan-review/approved/`. A rejection retires nothing. The record carries `schema: greenpiste-plan-approval-v1` and is documented in `docs/plan-review.md`. It is written with `write_atomic` to its own file keyed by `plan_id`, **before** `on_plan_answered` takes the ledger lock. So the hook's 2 s `skipped` path (review_outcomes.rs:502-514) still retires the id. The row for the approved body is recorded first, with the old id. A failed approval write is not fatal for the hook: its exit code and stdout are unchanged, and stderr says `plan-review: could not record approval of p-<id>: <error>`. Tests: the lock is held during an approval and the id is still retired; an unwritable store leaves the hook's exit code and stdout unchanged.
  - The next `plan-panel` on a file whose `plan-id` is approved, with a different body, replaces the id with a fresh one and prints `replaced plan-id p-<old> (approved) with p-<new>` on stderr.
  - So a plan edited into a new plan in the same file still gets a new id.
  - After a rejected ExitPlanMode the plan keeps its id, edited or not, so its next body is round 2.
- **Carried to the landed plan:** worktree-task already copies the front matter. The plan template gains a `plan-id:` line, filled from the plan-mode file.

### The ledger (`plan-review record`)
- Each row gains `plan_id`. `round` counts the bodies of that `plan_id` in ledger order, not transcript order, and `first_round_sha` is that id's first body.
- `plan-panel` stores body_sha → plan_id; `record` reads each row's id from that map, not from the current file.
- A body with no `plan-id` (written before this release) gets `plan_id: null` and the current behaviour.
- `plan` features gain `counts` (below).

### The baseline (`plan_review::baseline`, `save`)
- `save()` stores the `plan_id`.
- `baseline()` takes the `plan_id`. Its by-path and by-title fallbacks are used only when the stored id matches; a stored baseline with no id matches only a plan with no id, so `plan-panel` and the ExitPlanMode hook (`judge`, :1867) both seat a full panel for a new plan in a reused file.

### `stats --time`
- A landed plan with `plan-id:` is keyed to the ledger rows with that id: start, round-1 body and words come from them.
- A landed plan without one keeps today's path: the machine-comment `body-sha`, then `split_shared_starts`.

### relais (`review_outcome.rs`)
`Row` gains `plan_id: Option<String>` and `PlanFeatures` gains `counts: Option<serde_json::Value>`, both `#[serde(default)]`, so `deny_unknown_fields` keeps every new row. It also declares `plan.seat_source`, `plan.seat_classes` and `findings_unparsed`, which greenpiste already writes (review_outcomes.rs:709-710, :776) and relais rejects today. Unread fields are `_`-prefixed with `rename`. Tests: a row as greenpiste writes it parses, with every field, and an old row parses. Released and installed before greenpiste writes them.

### B5: counts
`plan-panel`'s first line ends with one token with no spaces, so the agent lines still start on line 2:

```
repos=… areas=… body=… panel=… seats=… counts=repos:3,phases:6,prs:3,releases:2,person:2,words:3100,merge-candidates:2+3;5+6
```

- `repos`: the machine comment's list.
- `phases`: `file_types::phases`.
- `prs`: the repositories the machine comment declares.
- `releases`: phases that name a version file (`Cargo.toml`, `package.json`, `plugin.json`, `pyproject.toml`, `greenharness.toml`) or the word "release" (any case). `CHANGELOG.md` alone does not count, because a feature phase adds its entry (this plan's Phase 3).
- `person`: 🧑 items under Phases.
- `words`: the `plan_words` count. From round 2 it is `words:3900/3100`, with the id's round-1 count.
- `merge-candidates`: adjacent phase pairs that name files in the same repositories, have the same file-type classes, and have no 🧑 item between them; `-` when there are none.

`record` stores the counts in `plan.counts`.

### `--time` follow-ups
- `clip` with `done` earlier than `start` uses an empty span.
- Stops, questions, PRs and releases count toward a plan only inside its span.
- The `src/main.rs` plan-review writer:
  - flushes stdout;
  - on a broken pipe, keeps the command's own exit code;
  - its SIGPIPE comment names `plan-review`.
- `clip` gets a unit table test.
- Exclusion labels are joined by `, `.

### Skills
- `plan-review` SKILL.md:
  - §0: `plan-panel` assigns `plan-id:`, so never edit or copy it by hand into a new plan;
  - §1: the first line ends with `counts=`;
  - §7: the 📍 line is `📍 <repositories> · <counts in words, or where the work stands once a phase ships> · next: <one action>. Panel: <roles with models>.`.
    - Counts read `6 phases`, `3 PRs`, `2 releases`, `2 steps for you`, `2 merge candidates`, `3100 words`.
    - It leaves out zero counts, uses the singular for 1, and names a model once when every seat ran on it (`Panel: backend, tui (opus-5-5)`).
    - It stays within about 20 words by dropping, in order: `words`, merge candidates, PRs when equal to the repository count, then the list of repositories (for `N repos`) when there are more than three.
    - Example, this plan: `📍 5 repos · 6 phases · 3 releases · next: Phase 1, relais reader. Panel: backend, lang:rust, unix, tui, architect (opus-5-5).`
- `worktree-task`'s `plan-template.md` gains `plan-id:` in the front matter.
- The `plan-review-backend` subtract step reads `merge-candidates`.

## Decision log
- 2026-11-15 — The person chose the redesign (a plan id) over the branch/H1 heuristic. The heuristic split plans by guessing; an id makes plan identity a fact.
- 2026-11-15 — The id lives in the front matter, because `body_sha` excludes it (reviews stay bound) and worktree-task already carries front matter to the landed plan.
- 2026-11-15 — The id is retired at approval, not by comparing titles, because the PostToolUse hook already sees each answered ExitPlanMode, its `approved` flag and its body.
- 2026-11-15 — relais first, as reader-first: its `Row` is `deny_unknown_fields`. An added field is otherwise a silent drop of every new row (architect, earlier panel).
- 2026-11-15 — No dependency on the 5.0.0 schema rename: `plan_id` is additive, and both schema names are read already.
